# Platform admin operations

September 15, 2026 UTC · Active implementation; no new production grant

## Existing owners

The console combines `SupportCase`, `CommunityReport` and `ChurchClaim` records.
It does not copy request bodies into a generic ticket store. Ordinary support
ownership binds to an active RESPOND grant and generation; ASSIGN alone sees only
unassigned routing metadata. Report access uses the existing original/current
church and topic scope predicate, including retention exclusions. Claim proof and
decisions retain their current independent-review and capability-subset checks.

An Admin entry belongs in Menu only when a current eligible account has a working
operator or scoped reviewer function. Every page, count, filter, lookup and action
checks current authority on the server. Neither an admin page nor a saved filter
grants access. The public five-destination navigation stays unchanged.

## Finishing scope

One bounded worklist orders native sources with stable continuation, current
status/type/owner/age/organization filters, private saved views and truthful empty
or unavailable states. Canonical sources retain their own versions, priority,
next action, internal tags and deliberate assignment. Assignment never grants
permission to read the source. Internal notes are separate from requester-visible
replies and cannot be turned into replies by editing their visibility.

Case pages preserve the filtered return and link to existing proof, moderation
and account workflows. Current native replies/transitions remain authoritative.
Duplicate grouping links original receipts without exposing another requester's
conversation. Bulk operations are bounded, reversible assignment/tag/status work;
each row rechecks permission and version and returns its own result. They cannot
approve claims, suspend accounts or permanently delete content.

New platform metrics, aggregate export, health, operational lookup, audit and
access-management responsibilities use separate explicit capabilities in the
existing grant model. Access administration requires current step-up proof,
version checks and an audit. The initial trusted assignment is an actual operator
prerequisite; fixture grants do not provision production. The existing account-
access owner decision remains open, and the settled sole-founder report-reviewer
policy is preserved.

Health reuses sanitized operational aggregates and marks unavailable/disabled
states truthfully. Metrics and feedback integrate through their owning features
when those contracts exist; no invented cards or new tracking is needed for the
worklist. Runtime review covers bounded source reads, request frequency, shipped
client code and actual provider package count.

## Current candidate and recovery behavior

The current source has six additive migrations (63 in the isolated fixture;
production remains 57 until a separately attested upgrade). Request counts reuse
the exact scoped source projection. Assignment filters check current reviewer
scope and the HMAC of the grant/membership generations recorded at assignment;
revocation followed by renewal requires an explicit reassignment. An unrelated
permission-generation change can conservatively invalidate an assignment too.
At most 100 distinct assigned reviewers are evaluated per scoped queue; larger
sets return an explicit unavailable result pending a measured scope-size review.

Saved views belong only to their owner and appear in that owner's private account
export. Internal notes never appear in requester exports or conversations. Opaque
retention controls clear stale internal fields on restoration without inventing a
native reply or appeal version. Leaving a duplicate group clears its shared title
and engineering link; the last departure deletes the group. Source deletion uses
the same database trigger. Each original source and immutable opaque audit remains
under its existing retention policy.

Only new access-management changes require the new authenticator. The existing
trusted process must first identify and assign a real MANAGE_ADMIN_ACCESS operator;
no name, account label or fixture grants that right. Each new change needs the
current grant generation, a fresh password or one-use Google purpose proof, the
specific target's expected grant version, a reason and an unused authenticator
code. Self-grant changes are unavailable in this interface. The one accepted
request key can be replayed without applying another change.

Enrollment uses an encrypted ten-minute key, an actual confirming code and eight
one-use recovery codes. A recovery needs both current sign-in confirmation and an
unused recovery code, retires the previous factor/codes and other sessions, and
requires confirming the replacement. Losing both factors requires trusted identity
review; email verification alone is not a bypass. Encrypted keys depend on the
protected AUTH_RATE_LIMIT_SECRET: rotate that secret only with a planned operator
reenrollment/recovery procedure. Restore retires authenticators, saved views,
operator grants and sessions rather than reviving backup credentials. Setup values
clear from browser memory after ten minutes and are never stored in local storage,
audit bodies or exports. QR failure retains manual key entry.

The authenticator matches the published [RFC 6238 test vectors](https://www.rfc-editor.org/rfc/rfc6238.html).
The fresh-authentication and recovery boundaries follow the existing account model
and the [OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).
Broader legacy privileged-MFA coverage remains separate from these new grant actions.
The [September 16 assessment](PRIVILEGED_AUTHENTICATION_ASSESSMENT.md) maps the
actual account/provider gap, every privileged authority, enrollment and recovery
policy, and the remaining provider-backed implementation/activation requirements.
It does not widen the current authenticator gate or alter existing grants.

The revised production preview passes five actual browser groups, including narrow
layouts, native resolve/reopen, retained selection, partial bulk results, authenticator
enrollment/confirmation and revoked-access concealment. Thirteen actual HTTPS/export/
release checks pass, and protected 57-to-63 production-copy recovery preserves all
102 original tables. The complete regression gate and exact canonical publication
remain pending. See [the current acceptance evidence](ADMIN_OPERATIONS_ACCEPTANCE.md)
for staged checks, retained failures, measured costs and real-operator limits.
