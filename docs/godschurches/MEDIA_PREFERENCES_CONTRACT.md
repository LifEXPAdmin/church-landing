# Media playback and upload preference capabilities

## Current scope and evidence

September 18, 2026 candidate, inspected against integrated `9e66724`. This is the capability and behavior map for autoplay, audio, captions, quality, data use and upload defaults. It adds no player, provider, preference persistence or upload format. The catalog resource is still reserved, and no supported audio/video player or caption-preference adapter exists in the inspected application. Future settings must distinguish that absence from a user's saved off choice.

The current media implementation is still-image processing and authorized delivery. `reading-preferences.ts` owns the browser-local `reduceData` choice. `profile-image.tsx`, `profile-photos.tsx`, `post-photos.tsx`, `exchange-photos.tsx` and `feedback-attachment-images.tsx` consume it on their supported image surfaces. The photo viewer loads the selected larger image after deliberate opening. This is not native audio/video playback or reliable network classification.

`media-processing.ts` accepts still JPEG, PNG or WebP, with a 4 MiB input and 40-million-pixel decoded limit. It rejects animations, re-encodes and strips metadata, and produces bounded original/large/medium/thumb WebP variants. Its “original” is a normalized image, not the original uploaded bytes. `media-access.ts`, `media-boundary.ts` and the owning source maintain authority; the existing upload form is not a generic audio/video or document uploader. Photo description/alt text and photo captions are distinct from timed media captions.

## Effective behavior and precedence

Resolve in this order: current source access and activation; actual adapter capabilities; current enforced policy where separately implemented; current browser reduced-motion/data constraints; saved user choice and a deliberate per-playback override; then browser/provider execution results. Distinguish requested from effective state and explain the reason for a mismatch. A result with unavailable or forbidden status contains no hidden value.

Reduced motion or the explicit reduced-data choice suppresses automatic starts and speculative next-item preloading in supported later players. It does not prevent a deliberate Play or Load action. Turning autoplay off while one item plays cancels queued automatic continuation; do not interrupt deliberate playback without telling the user. Leaving the supported player or losing source access cancels pending starts and releases that player's resources. Switching accounts must discard prior-account defaults and pending playback before loading new values.

For a direct, controllable media element, wait for the playback result before showing a playing state. Browser rejection should leave an accessible Play control and a clear explanation, not a timer repeatedly retrying or an unmuting workaround. Browser autoplay permission is independent of an app preference, and `play()` can reject when permission is absent. [MDN autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

For an accepted embedded player, declare supported control capabilities from its reviewed adapter; an iframe alone proves none. Apply only capabilities actually exposed by that provider in the current context. If it cannot honor an automatic-playback/data choice, use a deliberate external-link fallback or explain which settings cannot apply before loading it. Do not claim app controls govern playback in another browser tab or an external app. Provider privacy/consent checks remain independent of the preference.

The browser's native `textTracks` list reflects actual available tracks and can change as tracks load or disappear. The supported adapter must update the caption state when that list changes, keep captions independent of mute/volume, and provide a readable missing-track message. A preferred language cannot produce an absent translation. [MDN text-track reference](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/textTracks)

## Explicit data use and browser limitations

The reliable product choice is explicit Data saver, not a promise to detect every cellular connection. Network Information has limited browser availability. Its presence may provide a hint, but absence means unknown. The app must not equate effective speed with network type, infer the user's plan/cost, or label an unknown connection as Wi-Fi. This is an application contract based on the documented availability limit, not a claim that one browser exposes every network field. [MDN Network Information API](https://developer.mozilla.org/en-US/docs/Web/API/Network_Information_API)

Do not offer guaranteed “Wi-Fi only,” “never uses mobile data,” or universal automatic quality selection without a separately verified platform capability. If an optional hint is used later, disclose it as a hint and keep the explicit choice effective when the hint is missing or changes. No location request, carrier lookup, fingerprint, speed test or background probe is needed for this settings contract.

Data saver controls future requests the application actually owns. It cannot refund data already transferred, change a completed upload, rewrite provider media or guarantee zero network use. Thumbnail/manual-load behavior remains subject to source access. An explicit large-image request may consume additional data; describe that action plainly without weakening access or claiming exact savings from an unmeasured source.

## Upload, save and failure semantics

File selection is not permission to begin an unrelated background upload, upload a different file or select a wider audience. Preserve the existing explicit upload action, per-item progress, strict source checks, cancellation and retry receipts. A failed save/upload keeps the last confirmed settings and any safe local edit state; it does not silently fall back to the highest quality, a different provider or public visibility.

Snapshot accepted processing options with a new upload's canonical operation. Retrying that operation uses the same bytes and options; a changed setting or file requires a new deliberate request. A completed upload remains unchanged after preference edits. Existing media retention/removal applies to failed or replaced uploads; do not build a second cleanup policy or allow a preference to retain private files indefinitely.

Browser-local data saver stays local and contains no account identifier. Future account-level playback defaults require current owned-session persistence, expected-account checks, versions and exact-body retries. A local preview of an unsaved default is labeled preview and cannot claim the account value changed. Failed reads are unavailable, not default false. Scoped reset must tell the user which owner it changes and preserve unrelated display, notification, privacy and family choices.

## Interface and acceptance

In the single Media and data use settings layout, show supported playback choices first, captions independently from audio, then supported quality/data and upload choices. Omit unsupported upload options; use a concise unavailable explanation for an absent player. Do not put a functional-looking switch beside an unimplemented capability. Current data saver may link to/reuse the existing display owner. A future folder route must not duplicate its storage.

Each control exposes loading, current effective state, editable requested state, saving, saved, conflict and save failure where applicable. Keyboard and screen-reader users can reach caption controls without unmuting or starting playback. Announcements describe actual state, not a requested action that the provider/browser rejected. Respect enlarged text and reduced motion; preserve focus after a failed save and direct the user to a real retry or explicit external fallback.

Required adapter acceptance includes: OFF cancels automatic next; muted automatic playback never becomes audible without deliberate action; browser rejection preserves Play; no preloading before source/consent checks; real and missing caption tracks with independent audio controls; supported and unsupported quality modes; explicit data saver with network information absent; account switch and current source revocation; new-upload-only defaults; unchanged exact retries; provider failure without public/high-quality fallback; and no fake cellular, offline, savings or external-player-control claim.

The definition task changes only this contract and the matching inventory clarification. No runtime, schema, preference value, provider, migration or configuration changes. Eleven existing reading-preference and image-processing tests pass with no failures or skips, including unknown input, private-field exclusion, metadata stripping, animation rejection and streaming size limits. Current-source reconciliation, private-data/copy scans, formatting and diff checks pass. No new player, browser or full-suite acceptance is claimed for this document-only candidate. Player/caption/upload-preference activation, later settings implementation and verified release remain separate acceptance gates.
